AO E2E Test Platform

A cloud-agnostic, pod-per-run testing platform that acts as the end-to-end merge and release gate for Agent Orchestrator. Verdicts flow back into AO so agents can auto-fix failures without a human in the loop.

01Overview

The problem: Agent Orchestrator spawns fleets of AI coding agents, each producing PRs. Before a PR can merge (or a nightly build can ship), someone has to answer one question: does this commit actually work end to end? Today that answer is manual, slow, or missing entirely.

The platform answers it automatically. Every commit that needs testing gets a fresh, disposable Kubernetes pod in the dev team's own cloud account. The pod boots the app, runs the e2e suite, posts a pass/fail verdict as a GitHub commit check, uploads artifacts, and dies. No standing environments, no idle compute, no state leaking between runs.

The one-liner: a pod is born per commit tested, lives for minutes, and its only legacy is a verdict and a folder of artifacts. TrueFoundry built a hotel; we are building a food truck on the same road network.

Core design decisions

  • Pod per test run, not per PR. A PR with five pushes consumes five short-lived pods and zero compute in between. Between pushes there is nothing running.
  • No pod reuse, ever. Reused pods accumulate crud: leftover DB rows, stale dependencies, zombie processes. A merge gate's verdict must be trustworthy, so every run starts from a known-clean world.
  • Latency is solved below the pod. Warm node pool plus pre-pulled images gives roughly 15 second cold starts. Keeping pods alive to skip boot would pay hours of idle to save seconds.
  • GitHub is the messenger. No hosted control plane, no resident cluster agent in v1. The pod posts a commit check; AO's existing SCM polling picks it up like any CI status.
  • Runs in the dev team's own cloud subscription. Code and test data never leave their account. Multi-tenancy and data-residency problems are eliminated by construction.

02Components

Eight pieces, each with one job. Most are managed cloud primitives; only the runner image, the smoke suite, and the DeployTarget adapter are code we write.

COMPUTE

Kubernetes Cluster (EKS / GKE / AKS)

The universal substrate. One managed cluster in the team's cloud account. ECS was ruled out (AWS-only). Fargate and friends are just a capacity choice underneath, not an architecture decision.

COMPUTE

Warm Node Pool + Cluster Autoscaler

One or two always-on nodes with the base image pre-pulled so Jobs schedule in seconds. The autoscaler adds nodes under burst load and shrinks the pool when quiet.

EXECUTION

K8s Job (one per test run)

The unit of work. Job spec carries the commit sha, repo, and suite to run. Guardrails: activeDeadlineSeconds kills hung runs, ttlSecondsAfterFinished self-cleans finished pods, backoffLimit: 0 means no silent retries.

EXECUTION

Test Runner Image

Ubuntu + xvfb + Node + Playwright + the smoke/e2e suite. Per-repo dependencies are baked in and rebuilt only when the lockfile changes. Stored in the cloud's registry (ECR / GAR / ACR).

RELAY

GitHub Commit Check (ao-e2e-gate)

The verdict channel. The pod posts success or failure on the tested sha with a link to artifacts. Branch protection can require the check, which is what turns detection into an actual gate.

RELAY

Artifact Store (S3 / GCS / Blob)

Logs, screenshots, videos, junit reports. Artifacts outlive the pod so a failed run can be inspected long after the pod is gone. Lifecycle rules expire old runs automatically.

CONSUMER

Agent Orchestrator (unchanged core)

AO's existing SCM polling already watches PR checks. A red ao-e2e-gate flows into the lifecycle manager, the dashboard via SSE, notifiers, the agent fix loop, and eventually the Merge Autopilot trust dial. No new inbound plumbing.

ABSTRACTION

DeployTarget Port

A small interface (deploy / status / logs / teardown) between AO and the platform, matching AO's plugin-slot philosophy. The K8s backend is the first implementation, and it stays swappable.

03User Flow

Two flows share identical plumbing and differ only in the trigger: the nightly/weekly pilot (cron) and PR gating (push event).

Flow 1: Nightly / weekly build verification (the pilot)

Our nightly pipeline builds macOS, Windows, and Linux installers daily and publishes the auto-updater feed with zero post-publish verification today. Nothing ever installs what was just shipped. This makes it the perfect first customer: one run a day, nobody blocked if the platform flakes, and it fills a real gap on day one.

  • A PR with 5 pushes = 5 pods, each alive for minutes. Zero compute between pushes.
  • If a PR is closed or merged while a run is in flight, the Job is cancelled so we never finish testing a dead PR.
  • Artifacts outlive pods, so a red run from three days ago is still inspectable.

Platform coverage caveat (stated honestly)

Kubernetes pods are Linux containers. The pod executes only the Linux build for real. macOS cannot run in containers at all (Apple licensing), and Windows containers are impractical for Electron GUI testing. Mac and Windows legs get asset-existence, checksum, and feed-integrity checks only. Mitigant: the app's brain (Go daemon + identical JS renderer) is the same on every platform, so most regressions are cross-platform and the Linux smoke run catches them. True Mac/Windows execution coverage later means GitHub-hosted runners posting to the same check.

04State Management and Component Interaction

Principle: no new database, no new state store. Every piece of state already has a natural home, and each component owns exactly one kind of state. The platform adds a state machine, not a stateful service.

Who owns what

Test run execution stateKubernetes (Job status: Pending, Active, Succeeded, Failed)Until Job TTL reaps it (minutes to hours)

Test run state machine

stateDiagram-v2 [*] --> Queued: trigger fires (push / cron) Queued --> Provisioning: Job submitted to cluster Provisioning --> Running: pod scheduled on warm node (~15s) Running --> Reporting: suite finished Running --> TimedOut: activeDeadlineSeconds hit Running --> Cancelled: PR closed or merged mid-run Reporting --> Passed: check posted green Reporting --> Failed: check posted red TimedOut --> Failed: check posted red (timeout) Cancelled --> [*]: Job deleted, no check posted Passed --> [*]: pod dies, TTL cleanup Failed --> [*]: pod dies, artifacts retained

How the components interact (interaction contract)

  1. Trigger to platform: a workflow step (or later, webhook receiver) submits a Job spec. The only payload is repo + sha + suite name. Fire and forget.
  2. Platform to pod: Kubernetes owns scheduling, retries (disabled), timeouts, and cleanup. We do not build a scheduler; we configure one.
  3. Pod to the world: the pod is the only writer of verdicts and artifacts. It posts the check and uploads evidence before exiting. If the pod dies without posting, the Job's failure state plus a small watcher marks the check red with reason "runner error", so a crash can never masquerade as a pass.
  4. GitHub to AO: AO's existing SCM polling reads checks on PR heads exactly as it reads CI today. Red gate lands in the lifecycle manager, which flags the session (ci_failed path), streams to the dashboard over SSE, fires notifiers, and hands the failure to the agent fix loop. Zero new inbound plumbing into AO.
  5. AO to cluster (operational only): a kubeconfig-scoped poll for babysitting: stuck Jobs, queue depth, node health. Never used for verdicts; verdicts only travel through GitHub so there is exactly one source of truth.
Why verdict-through-GitHub matters: it makes the platform crash-safe and restart-safe. If AO restarts, the check is still on the commit. If the platform is rebuilt from scratch, no verdict history is lost. The commit itself carries its own test record.

05The TrueFoundry Playbook: What We Took, What We Skipped

TrueFoundry solved a neighboring problem: run ML workloads in the customer's own cloud, cloud-agnostically, with a good enterprise security story. We studied their architecture deliberately.

How TrueFoundry does it today

  • Split-plane architecture. A control plane (API, metadata, RBAC, dashboards; hosted by them or self-hosted) and a compute plane (the customer's own Kubernetes cluster where workloads actually run).
  • Resident cluster agent (tfy-agent). Installed in the customer cluster, it opens an outbound-only connection to the control plane. The customer never exposes an inbound port and never hands out a kubeconfig. This is a security argument built for enterprise procurement.
  • GitOps deploys via ArgoCD, workload identity instead of long-lived keys, and integrations into the customer's own secret managers.
  • Center of gravity: long-lived services. A deployed model API becomes a Kubernetes Deployment with ingress, URLs, autoscaling, and rollout strategies. It stays up until torn down. They also offer a Jobs type for batch and training work, which is run-and-die like ours, but the surrounding machinery is built for residents, not visitors.

The page we took from their playbook

Borrowed ideaTheir versionOur version
Compute in the customer's cloud, K8s as the universal substrate Customer's EKS/GKE/AKS cluster runs all workloads; clouds become interchangeable Identical. This is the core of both cloud-agnosticism and scaling for us
Workload identity over static keys Cloud IAM bound to service accounts IRSA / Workload Identity Federation / Azure WI for artifact upload; no keys in images
Scoped, short-lived credentials Secret-manager integrations, per-workspace tokens Read-only deploy token per repo, short-lived GitHub App token for checks
The outbound-only agent pattern tfy-agent, in production today Deliberately deferred to a later version (see roadmap). We know exactly what to build when a customer's security review demands it

The pages we deliberately did not take

Their machineryWhy we skip it (for now)
Hosted control planeA SaaS brain must command customer clusters continuously. We do not need continuous command: GitHub is our messenger. The commit check plus AO's existing polling replaces the entire relay layer.
Resident cluster agentExists to serve the hosted control plane. No control plane, no agent. It becomes worth building only for BYOC customers with strict security reviews.
Ingress, URLs, autoscaling policies, rollout strategiesAll built for workloads that live. Our workload has a natural ending (the verdict), so a K8s Job with a TTL replaces all of it.
SSO / RBAC / multi-tenant product layerThey serve many customers from one control plane. Everything of ours runs inside one team's account; the trust boundary conversation is one sentence.
Honest note: TrueFoundry's outbound-agent design is genuinely the better enterprise pattern. Security teams hate handing out kubeconfigs; "install this agent, it only dials out" clears procurement far more easily. That is precisely why it is on our roadmap (v3) rather than in v1: it is the right machinery, currently without a customer.

06How Exactly It Is Cloud Agnostic

Cloud-agnosticism is not a slogan here; it falls out of one decision: everything above the node is Kubernetes, and everything below the node is somebody's managed service.

The portable layer (identical on every cloud)

  • Job specs, pod specs, resource limits, TTLs, deadlines: plain Kubernetes YAML
  • The test runner image: standard OCI container, runs anywhere
  • NetworkPolicies, secrets mounting, service accounts: core K8s primitives
  • The verdict relay: GitHub and object storage APIs, no cloud-specific calls in the pod

The per-cloud adapter (thin, Terraform-shaped)

ConcernAWSGCPAzure
Managed K8sEKSGKEAKS
Image registryECRArtifact RegistryACR
Artifact storeS3GCSBlob Storage
Workload identityIRSAWorkload Identity FederationAzure Workload Identity
Serverless capacity (optional)Fargate profilesGKE AutopilotAKS virtual nodes

Each column is one Terraform module. The Job specs, the runner image, the smoke suite, and the relay logic do not change by a single line across columns. Supporting a new cloud means writing one more module, not touching the platform.

Why ECS lost: ECS is a fine scheduler, but it is AWS-only. Choosing it would have welded the whole platform to one column of the table above. Kubernetes makes the columns interchangeable, and Fargate-style serverless capacity is still available under K8s where we want it.

The DeployTarget port keeps even K8s swappable

AO talks to the platform through a four-verb interface: deploy(spec), status(runId), logs(runId), teardown(runId). Kubernetes is the first implementation. If a customer someday wants Nomad, bare VMs, or a fully hosted runner fleet, that is a new adapter behind the same port, matching AO's existing plugin-slot philosophy (runtime, agent, workspace, tracker, SCM, notifier are already pluggable).

07Scaling: What Happens at 100+ Pods

The stress case: a dev team with 10 repos, each with 10 active PRs, agents pushing fixes all day. Naive designs keep 100 environments alive. Ours keeps zero.

Why 100 "active PRs" does not mean 100 pods

Pods exist per run in flight, not per open PR. A PR is open for days but tested for minutes. Even with 100 open PRs, concurrent runs at any instant are driven by push frequency. If agents collectively push 40 times an hour and a run takes 9 minutes, steady-state concurrency is about 6 pods. Bursts (an agent fleet all pushing after a shared fix) spike higher, and that is exactly what the autoscaler absorbs.

The scaling mechanics, layer by layer

LayerMechanismBehavior under burst
AdmissionJob queue with a concurrency cap (namespace ResourceQuota)Runs beyond the cap wait in Queued; nothing falls over, verdicts are just a few minutes later
SchedulingWarm node pool (1-2 nodes, base image pre-pulled)First N pods start in ~15 seconds
CapacityCluster autoscaler / KarpenterBurst beyond warm capacity adds nodes in 1-2 minutes, then drains them when quiet
IsolationOne pod per run, resource requests + limits per podA pathological test (memory leak, fork bomb) is contained and OOM-killed inside its own pod; 99 other runs unaffected
Fairness across reposPer-repo quota sliceOne chatty repo cannot starve nine quiet ones
Cost floorScale-to-warm-pool, not scale-to-100Nights and weekends cost 1-2 small nodes, not a fleet

The numbers that make pod-per-run win

  • 100 alive PR-pods (4 vCPU / 8 GB each): roughly 400 vCPU reserved 24/7, at ~1% useful utilization. You pay hours of idle to save 15 seconds of boot per run.
  • Pod-per-run at the same load: single-digit concurrent pods on 2-6 nodes, scaling to zero-plus-warm-pool overnight. Cost tracks test minutes, not PR lifetime.
  • State safety is the hidden win: at 100 reused pods, "was the failure the commit's fault or the last run's leftovers" becomes a daily debugging tax. Fresh pods make it structurally impossible.
Rule of thumb: scale nodes, never lifetimes. Any latency problem gets solved below the pod (warmer nodes, better image caching, baked dependencies), and any throughput problem gets solved beside it (more nodes). Pod lifetime stays: born per commit, dead at verdict.

08Roadmap: v0 to v4

Each version is independently shippable and independently valuable. We never build machinery ahead of the customer who needs it.

v0

Nightly Detector (internal pilot)

Goal: prove the pipeline on a workload where a flake blocks nobody.

  • One cluster, one warm node, one runner image
  • Nightly workflow triggers a K8s Job after publish; pod downloads the Linux nightly, installs, boots headless, runs smoke e2e, verifies updater-feed integrity for all three platforms
  • Posts ao-nightly-gate commit status + artifacts, then dies
  • Detection only: a bad nightly is flagged, not blocked
  • Exit criteria: two weeks of nightly verdicts with zero false reds
v1

Release Gate (nightly + weekly/stable)

Goal: a bad build cannot ship.

  • Publish releases as drafts; promote the updater feed only on a green gate
  • Same flow extended to the tag-driven stable/weekly release (higher stakes, biggest payoff)
  • Crash-safe verdicts: a runner crash marks the check red, never silently passes
  • Artifact retention policies and a simple run-history view (links from the check)
v2

PR Merge Gate + AO Integration (first external teams)

Goal: the platform becomes AO's e2e merge gate; agents auto-fix red gates.

  • Trigger on PR pushes; one pod per commit tested; cancel in-flight runs when a PR closes
  • ao-e2e-gate required via branch protection
  • AO SCM poll consumes verdicts into the lifecycle manager: dashboard, notifiers, agent fix loop
  • DeployTarget port formalized; Terraform onboarding module per cloud (EKS / GKE / AKS)
  • Per-repo quotas and concurrency caps for multi-repo teams
  • Feeds the Merge Autopilot trust dial: green gate + trust level = no-touch merge
v3

Hosted Relay + Outbound Agent (enterprise BYOC)

Goal: pass enterprise security reviews; sell to teams where the AO user does not own the cluster.

  • This is where we adopt the TrueFoundry tfy-agent pattern: a small resident agent in the customer cluster, outbound-only connection, no kubeconfig handed out
  • Hosted ingest endpoint for real-time log streaming and run events (replaces polling where teams want live tails)
  • Multi-service test stacks: app + db + browser-runner as multi-container pods sharing localhost, for repos whose e2e needs a real stack
  • Optional Mac/Windows execution legs via GitHub-hosted runners posting to the same check
v4

Test Platform as a Product

Goal: the gate is the product, sold beyond AO users.

  • Preview environments (the Flow B we deliberately skipped): standing per-PR stacks with URLs, for teams that want humans clicking, killed on merge/close
  • Flake intelligence: quarantine known-flaky tests, auto-retry policies with evidence, trend dashboards
  • Conflict Radar integration: pairwise merge-tree analysis across agent sessions feeding the same trust dial
  • Multi-cloud failover and org-level RBAC (the last TrueFoundry pages, taken only when customers demand them)

09Future Scope and Open Questions

Multi-service stacks in one pod

App + database + test runner as sidecars sharing localhost stretches pod-per-run surprisingly far before anything like a preview environment is needed. Where is the cutoff? Likely: when a human needs a URL.

Warm pods with hard cleanup (idle TTL)

If 15-second cold starts ever measurably hurt, a 10-minute idle TTL with a mandatory wipe step between runs is the compromise. Deliberately not in v0-v2: it reintroduces state-leak risk for a latency win nobody has asked for yet.

Mac and Windows execution coverage

Containers cannot cover these legs. Options ranked: GitHub-hosted runners (easy, already used for builds), EC2 Mac instances (expensive, 24h minimum), a small self-hosted runner pool. All post to the same commit check.

Verdict-quality metrics

The gate is only as good as its false-positive rate. Track: false reds per hundred runs, time-to-verdict p50/p95, artifact usefulness on failures. These numbers decide when the trust dial can go fully no-touch.

Cost observability

Per-run cost tagging (repo, PR, sha) so a team can see exactly what their gate costs and which repo's suite is the expensive one. Cheap to add early, painful to retrofit.

Beyond GitHub

The relay is a commit check today. GitLab and Bitbucket equivalents exist and slot behind AO's SCM plugin abstraction when a customer brings them.
